# Graph-Based Anti-Money-Laundering (AML) Analytics Platform

A single-file, locally runnable prototype that represents a bank's ledger as
an **account graph** instead of a table of isolated transactions, and uses
graph structure — cycles, fan-out/fan-in, centrality, community membership —
to flag accounts that look like they're part of a money-laundering network.

> **This is a portfolio / research project built on 100% synthetic data.**
> It does not claim regulatory compliance, and it is not a substitute for a
> licensed AML system. See [Limitations](#limitations) below.

```
python aml_graph.py
```

Everything — data generation, graph construction, feature engineering,
modeling, evaluation, and investigation output — lives in **`aml_graph.py`**.
There is no notebook, no frontend, and no second Python file.

---

## 1. The AML Problem

Banks and payment processors must detect money laundering: the process of
disguising the origin of illegally obtained funds by moving them through a
series of transactions until they appear legitimate. Regulators require
institutions to monitor transactions and file Suspicious Activity Reports
(SARs) when patterns look like laundering typologies (structuring, layering,
smurfing, trade-based laundering, mule networks, etc.).

The operational reality investigators deal with is **alert-driven**: a
monitoring system raises alerts, and a human investigator has to work each
one. That means **precision matters enormously** — every false alert is
analyst time that isn't spent on a real case — while recall still has to be
high enough that real laundering doesn't slip through.

## 2. Traditional Transaction Monitoring vs. Graph-Based AML

**Traditional approach:**

```
Transaction → transaction-level features (amount, time, type) → rules / ML → alert
```

Each transaction is scored independently. This works well for simple
threshold rules (e.g. "flag any wire over $10,000") but struggles with
laundering typologies that are only visible when you look at *how money
moves between accounts*: a single $9,000 deposit looks fine in isolation,
but ten $9,000 deposits from the same account in three days is structuring;
a $50,000 wire looks fine, but that same $50,000 bouncing A→B→C→A in 45
minutes is layering.

**This project's approach:**

```
Transactions → Account Graph → Graph Features → ML / Risk Model
             → Suspicious Accounts → Investigation Network
```

Instead of scoring a transaction, we score an **account**, using both its
own transactional aggregates *and* the shape of its neighborhood in the
whole transaction graph (who it's connected to, how central it is, whether
it sits on a cycle, whether it fans money out to many new accounts at once).

## 3. Synthetic Data Generation

**The dataset is entirely synthetic**, generated by `TransactionGenerator`.
There is no real financial data anywhere in this project.

- **Normal behaviour**: ~3,000 peer-to-peer transactions among 250 "normal"
  accounts, with log-normal transaction amounts, a realistic mix of
  transaction types (`WIRE`, `CARD`, `UPI`, `ACH`, `CASH_DEPOSIT`), and a
  country distribution weighted toward domestic activity.
- **Injected laundering typologies** (see next section) are added on top,
  each creating new accounts and transactions that follow a specific,
  named topology.

Crucially: **suspicious labels are never assigned randomly.** An account is
only in the ground-truth suspicious set if it was placed inside one of the
injected patterns below. This label exists purely so we can *evaluate*
whether graph features carry signal — it is never used as an input feature.

## 4. Suspicious-Pattern Generation

Six typologies are injected, each with its own generator method:

| Pattern | Method | Description |
|---|---|---|
| **Circular flow** | `inject_circular_flows` | A → B → C → A, with a small "skim" at each hop, all within ~30 minutes — classic layering. |
| **Fan-out** | `inject_fan_out` | One hub account rapidly disperses funds to several new accounts — mirrors smurf/mule distribution. |
| **Fan-in** | `inject_fan_in` | Several new accounts rapidly funnel funds into one hub — mirrors cash aggregation. |
| **Rapid pass-through** | `inject_rapid_passthrough` | A → B → C within minutes, with the amount nearly unchanged — a classic mule chain. |
| **Structuring** | `inject_structuring` | 6–10 transactions per account, each 90–99% of a $10,000 threshold, spread over ~3 days — avoiding a reporting threshold. |
| **Unusual cross-border** | `inject_unusual_cross_border` | Large, frequent wires to offshore/shell-heavy jurisdictions (Cayman Islands, Bermuda, Panama). |

## 5. Graph Representation

- **Node** = account (`account_id`)
- **Edge** = transaction, with attributes: `amount`, `timestamp`, `country`,
  `transaction_type`, `txn_id`
- Stored as a `networkx.MultiDiGraph` (`TransactionGraph.graph`), preserving
  every individual transaction as its own edge, plus a collapsed
  `simple_graph()` view (one edge per ordered account pair, amount summed)
  used for most graph algorithms.

### Why NetworkX?

NetworkX was used because it ships pure-Python implementations of every
algorithm this project needs (PageRank, degree/betweenness centrality,
greedy-modularity community detection, weakly-connected components) with no
extra infrastructure, it consumes pandas edge lists directly, and at
portfolio scale (a few hundred nodes, a few thousand edges) its pure-Python
performance is entirely adequate — it runs identically on any machine,
satisfying the "runs locally" constraint without a GPU-graph dependency like
cuGraph.

## 6. Graph Algorithms

Implemented in `TransactionGraph` and `GraphFeatureEngineer`:

- **Weakly connected components** (`nx.weakly_connected_components`)
- **PageRank** (`nx.pagerank`)
- **Degree centrality** (`nx.degree_centrality`)
- **Betweenness centrality** (`nx.betweenness_centrality`, with k-sampling
  approximation above 400 nodes to keep runtime bounded)
- **Clustering coefficient** on the undirected projection (`nx.clustering`)
- **Community detection** (`nx.algorithms.community.greedy_modularity_communities`)
- **Bounded-depth cycle detection** (`TransactionGraph.short_cycles`): a
  custom DFS that only enumerates simple cycles up to length 4. A full
  `nx.simple_cycles()` over the raw graph is combinatorially expensive and
  not what AML typology needs anyway — laundering rings are deliberately
  kept short (2–5 hops) because every extra hop dilutes the funds and adds
  detection surface for the launderer.

## 7. Feature Engineering

`GraphFeatureEngineer.build_features()` produces one row per account with:

- Topology: `in_degree`, `out_degree`, `total_degree`, `pagerank`,
  `degree_centrality`, `betweenness_centrality`, `clustering_coeff`,
  `community_id`, `community_size`, `short_cycle_count`
- Ledger aggregates: `total_in_amount`, `total_out_amount`, `net_flow`,
  `unique_in_counterparties`, `unique_out_counterparties`, `n_transactions`
- Behavioural ratios: `fan_in_ratio`, `fan_out_ratio` (unique counterparties
  ÷ degree — near 1.0 means every edge goes to a *different* account, a fan
  signature; near 0 means repeated transfers to the same few accounts),
  `txn_velocity_per_hr`, `structuring_ratio` (fraction of outgoing
  transactions sitting just under the $10,000 threshold),
  `high_risk_country_ratio`

None of these features reference the ground-truth label.

## 8. ML Methodology

`AMLScorer` compares three approaches on the same feature table:

1. **Rule-based scoring** — a fixed weighted sum of normalized graph signals
   (fan-out, fan-in, cycle count, structuring ratio, high-risk-country
   ratio, velocity), alerting on the top 10% by score. This mirrors what a
   lot of legacy AML systems run in production today: transparent and cheap,
   but rigid.
2. **Logistic Regression** (`class_weight="balanced"`) — a simple, linear,
   auditable model. Regulators and model-risk teams favor models whose
   coefficients can be explained per account.
3. **Random Forest** (300 trees, depth 8, `class_weight="balanced_subsample"`)
   — a non-linear model that can capture feature interactions (e.g. high
   fan-out *and* a short cycle *and* near-threshold amounts together, which
   no single rule threshold catches cleanly).

A stratified 70/30 train/test split is used at the account level. A
lightweight GraphSAGE/GNN was intentionally **not** built: with a few hundred
nodes and a handful of hand-engineered structural features already
available, a GNN would not add a clean, well-justified improvement here —
see [Possible GNN Extension](#possible-gnn-extension) for when it would.

## 9. Evaluation

Because AML investigations are alert-driven, **precision and investigator
workload** are emphasized alongside recall. All numbers below are from an
actual run of `python aml_graph.py` (`RANDOM_SEED = 42`) — nothing is
hand-typed or fabricated.

**Dataset produced by this run:**

| Metric | Value |
|---|---|
| Accounts | 382 |
| Transactions | 3,167 |
| Ground-truth suspicious accounts | 58 (15.2%) |
| Weakly connected components | 29 (largest: 256 accounts) |

**Model comparison (held-out test set, 115 accounts):**

| Model | Precision | Recall | F1 | PR-AUC | Precision@10% | Alerts |
|---|---|---|---|---|---|---|
| Rule-Based | 0.111 | 0.059 | 0.077 | 0.127 | 0.091 | 9 |
| Logistic Regression | 1.000 | 0.941 | 0.970 | 1.000 | 1.000 | 16 |
| Random Forest | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 17 |

**Confusion matrices `[[TN, FP], [FN, TP]]`:**

- Rule-Based: `[[90, 8], [16, 1]]`
- Logistic Regression: `[[98, 0], [1, 16]]`
- Random Forest: `[[98, 0], [0, 17]]`

**Top graph features by Random Forest importance:** `txn_velocity_per_hr`,
`community_size`, `degree_centrality`, `n_transactions`,
`betweenness_centrality`, `total_degree`, `short_cycle_count`,
`total_out_amount` — a mix of topology and ledger-aggregate features,
confirming graph structure is genuinely contributing, not just amount/volume.

**Alert workload:** the best model (Random Forest) generated 17 alerts out
of 115 test-set accounts (**14.8%** of the book), with 0 false alerts on
this run.

### Reading these numbers honestly

The ML models' near-perfect scores are a direct result of how the synthetic
patterns were injected: each typology creates small, topologically distinct
clusters (isolated 3-node rings, star-shaped hubs, short chains) that sit
clearly apart from the randomly-connected "normal" population. That makes
this an easy separation problem for a graph-aware model — the point of the
exercise is to demonstrate *that graph structure carries the signal*, not to
claim real-world laundering is this easy to catch. In a live system, real
launderers deliberately blend their activity into normal-looking volume,
typologies overlap and mutate, and labels are scarce and noisy — see
[Limitations](#limitations). The rule-based baseline's poor recall (5.9%) is
realistic, though: fixed-threshold rules genuinely do miss most non-obvious
structuring/layering activity, which is exactly why banks invest in
graph/ML-based monitoring on top of rules rather than instead of them.

## 10. Investigation Workflow

`InvestigationEngine.investigate(account_id)` takes the highest-risk account
(by the best model's score) and produces a plain-text packet: risk score,
direct counterparties, suspicious cycles it sits on, total flow, transaction
velocity, centrality measures, other accounts connected via those cycles,
and its most recent transactions.

### Example investigation output (actual output from this run)

```
Account RING0_0
Risk Score: 1.00

Direct outgoing counterparties (1): ['RING0_1']
Direct incoming counterparties (1): ['RING0_2']

Suspicious relationships (short cycles found):
  RING0_0 -> RING0_1 -> RING0_2 -> RING0_0

Total flow through account: ₹47,398.74
  Total incoming: ₹23,812.03
  Total outgoing: ₹23,586.71

Velocity: 2 transactions within 30.0 minutes

Centrality measures:
  PageRank: 0.00336
  Degree centrality: 0.00525
  Betweenness centrality: 0.00001
  Clustering coefficient: 1.00000

Connected suspicious accounts (2): ['RING0_1', 'RING0_2']

Recent transactions:
  [OUT] 2024-03-26 06:42 ₹23,586.71 <-> RING0_1 (WIRE, IN)
  [IN] 2024-03-26 07:12 ₹23,812.03 <-> RING0_2 (WIRE, IN)
```

The system correctly recovered the injected A→B→C→A circular-flow ring and
reported near-1.0 clustering coefficient (the account's neighbors are
themselves connected — the signature of a closed ring) despite very low
degree and betweenness centrality, since the ring is a small, otherwise
disconnected component of the overall graph.

## 11. Architecture

All logic lives in `aml_graph.py`, organized into five classes used in a
linear pipeline from `main()`:

```
TransactionGenerator ──▶ TransactionGraph ──▶ GraphFeatureEngineer
                                                     │
                                                     ▼
                                                 AMLScorer
                                                     │
                                                     ▼
                                          InvestigationEngine
```

```
Transactions (pandas DataFrame)
        │
        ▼
┌───────────────────┐     node = account
│  TransactionGraph  │     edge = transaction (amount, ts, country, type)
│  (networkx graph)  │
└─────────┬──────────┘
          │  simple_graph(), short_cycles(), connected_components()
          ▼
┌────────────────────────┐   degree / centrality / community / cycles
│  GraphFeatureEngineer   │   + ledger aggregates (amounts, velocity, ratios)
└─────────┬───────────────┘
          │  node-level feature table
          ▼
┌───────────────────┐   Rule-Based vs Logistic Regression vs Random Forest
│     AMLScorer      │   precision / recall / F1 / PR-AUC / precision@K
└─────────┬───────────┘
          │  risk_scores per account
          ▼
┌────────────────────────┐   direct counterparties, cycles, velocity,
│  InvestigationEngine    │   centrality, connected suspicious accounts
└────────────────────────┘
```


## 14. Limitations

This is a **research/portfolio prototype**, not a production or
regulatory-compliant AML system. It makes no claim of meeting BSA/AML, FATF,
FinCEN, EU AMLD, or any other regulatory framework. In particular:

- **The dataset is entirely synthetic.** Real transaction graphs are far
  larger, noisier, and less cleanly separable than the patterns injected
  here (see the "reading these numbers honestly" note in Evaluation).
- **Labels don't exist a priori in real AML.** This project can generate
  ground-truth labels because *it* injected the patterns. Real systems
  operate with sparse, delayed, and noisy labels (SAR filings, closed
  investigations) and often no labels at all for novel typologies.
- **No KYC/CDD data.** Real AML systems join transaction graphs with
  Know-Your-Customer and Customer Due Diligence data (beneficial ownership,
  occupation, expected activity) to contextualize what "unusual" means for
  a specific customer.
- **No sanctions/watchlist screening**, which is a separate, mandatory
  control (OFAC, UN, EU lists) that operates independently of behavioral
  monitoring.
- **No regulatory rule engine.** Jurisdictions mandate specific rules (e.g.
  currency transaction reporting thresholds) that must be implemented
  exactly, not approximated by ML.
- **No human investigation or case management workflow.** Every alert here
  is illustrative text; a real system routes alerts into a case management
  platform with SLAs, escalation, and disposition tracking.
- **No audit trail.** Regulators require an auditable record of why each
  alert was raised, who reviewed it, and what action was taken — this
  prototype does not persist or version any of that.
- **Graph algorithms are not incremental.** Centrality and cycle detection
  are recomputed from scratch; a production system would need streaming or
  incremental graph updates as new transactions arrive in real time.

## 15. Production Architecture (sketch)

A production-grade version of this idea would typically look like:

```
Core banking / payments  ──▶  Streaming ingestion (Kafka/Kinesis)
                                     │
                                     ▼
                        Graph database (Neo4j / TigerGraph / Amazon Neptune)
                                     │
                     ┌───────────────┼───────────────────┐
                     ▼               ▼                    ▼
        Incremental graph      KYC/CDD & sanctions   Regulatory rule
        feature pipeline       data enrichment        engine (thresholds,
        (streaming)                                   jurisdiction-specific)
                     │               │                    │
                     └───────────────┴───────────┬────────┘
                                                  ▼
                                    Risk scoring service
                                    (rules + ML ensemble,
                                     model governance/monitoring)
                                                  │
                                                  ▼
                                    Case management system
                                    (alert triage, SLAs, audit trail,
                                     SAR filing workflow, feedback loop
                                     to retrain models on investigator
                                     dispositions)
```

Key differences from this prototype: incremental/streaming graph updates
instead of batch recomputation, a real graph database instead of in-memory
NetworkX, human-in-the-loop feedback that actually updates the label
distribution over time, and strict model governance (explainability,
bias testing, periodic revalidation) required for any model influencing
regulatory filings.

## 16. Possible GNN Extension

This project deliberately does **not** force a Graph Neural Network, per the
project brief — the goal was to show that graph *structure*, expressed as
engineered features, already provides strong signal, and a GNN was not
needed to make that case with a graph this size.

A GNN would become a more natural choice if:

- The graph were large enough (hundreds of thousands to millions of nodes)
  that hand-engineered features became a bottleneck rather than the model.
- Node/edge features were richer (e.g. free-text memo fields, merchant
  category embeddings) such that learned representations could outperform
  hand-crafted aggregates.
- The task shifted from node classification to **link prediction** (will
  this pair of accounts transact?) or **temporal graph modeling** (does the
  *sequence* of graph changes over time predict laundering onset before a
  static snapshot would) — both are natural fits for GraphSAGE-style
  inductive learning, which generalizes to new/unseen accounts without
  retraining from scratch, unlike this prototype's batch feature table.

A lightweight next step, without adding a deep-learning framework, would be
to use `GraphFeatureEngineer`'s output as node embeddings and feed sequences
of a node's feature vectors over rolling time windows into a simple
recurrent or gradient-boosted temporal model, before reaching for a full GNN
stack (PyTorch Geometric / DGL).

## 17. Interview Questions

Questions this project is designed to prepare you to answer well:

1. Why is transaction-level monitoring insufficient for layering and
   smurfing typologies, and what does a graph view add?
2. Walk through how PageRank, betweenness centrality, and clustering
   coefficient each capture a *different* kind of suspicious structure.
   Which would you expect to fire for a circular-flow ring vs. a fan-out hub?
3. Why does this project cap cycle detection at length 4 instead of running
   full `simple_cycles()`? What's the complexity trade-off, and is the cap
   a modeling choice or purely a performance one?
4. The Random Forest reaches perfect precision/recall on this dataset. Is
   that a good sign or a red flag, and how would you validate a model like
   this before trusting it in production?
5. Why is precision emphasized over recall in an alert-driven AML system,
   and what's the cost model behind that trade-off?
6. How would you turn this batch pipeline into a streaming system that
   scores accounts as new transactions arrive, without recomputing global
   centrality from scratch every time?
7. What's the difference between a rule-based AML system and this
   ML-on-graph-features approach in terms of regulatory explainability, and
   how might you combine both in a real deployment?
8. If you had real (unlabeled, or weakly labeled) transaction data, how
   would you validate that your injected-pattern approach to generating
   synthetic labels transfers to real laundering behavior?
9. When would you reach for a GNN over hand-engineered graph features, and
   what would the engineering cost of that upgrade look like?
10. What additional data sources (KYC, sanctions lists, device/IP graphs)
    would most improve this system's real-world precision, and why?
